## Open-ended project progress

A major design decision was made around project progress.

OnProgram does **not** assume that users know the final number of tasks before beginning a project.

Instead, progress represents:

```
Current linked work
completed / currently linked
```

This means a project can show something like:

```
4 / 6
█████████████──────
```

without claiming that the project itself is objectively 67% complete.

The denominator is allowed to grow or shrink as work is discovered.

Progress rules:

- `done` counts as completed
- `posted` counts as completed
- `cancelled` is excluded from the denominator
- `archived` is excluded from the denominator
- all other currently linked tasks remain part of current work

This model preserves the reality that real projects evolve.

## Robust project references

Project linkage was made tolerant of different Markdown reference styles.

A project reference can match using:

- full file path
- basename
- project title
- `.md` paths
- Obsidian wiki-link syntax
- aliased wiki links

That makes project assignment less brittle as users work naturally inside a vault.

## Project Task Manager

Added a dedicated Project Task Manager.

From a project, users can now:

- create a new task already linked to the project
- see the current project checklist
- complete tasks
- reopen completed tasks
- remove a task from the project without deleting it
- search existing tasks
- attach an unassigned task
- move a task from another project into the current project

The task manager deliberately keeps two concepts separate:

1. **Project membership**
2. **Task completion**

A checkbox means the task is complete. Attaching a task means the task belongs to the project. Those are not treated as the same operation.

## Shared Project assignment workflow

Project assignment was extended beyond the Projects view.

The rule established for OnProgram is:

A shared Project assignment flow was added so users can assign or reassign tasks without manually editing YAML.

# 4. Made the Dashboard Customizable

The Dashboard was expanded from a fixed layout into a configurable workspace.

## Width modes

Added:

```
Centered | Full width
```

Centered mode preserves a more compact command-center layout.

Full Width mode uses more of the Obsidian workspace, particularly useful on ultrawide displays.

The width preference is stored per Dashboard view.

## Customize Dashboard

Added a Dashboard customization panel that supports:

- drag-and-drop section reordering
- move up / move down controls
- hide/show individual sections
- Half Row sizing
- Full Row sizing
- reset to default layout

## Per-view persistence

Dashboard layout configuration is stored with the Dashboard view configuration rather than globally.

That means different Bases can have different Dashboard arrangements.

For example, a Content Dashboard and an SMP Dashboard can be organized differently.

## Responsive widget behavior

Heavier widgets adapt when placed at half width.

Examples:

- Board becomes more vertically compact
- Calendar becomes horizontally scrollable rather than crushing seven days into a narrow space

# 9. Added Half-Hour Calendar Drag Feedback

The Calendar already supported dropping timed tasks at either:

- `:00`
- `:30`

The problem was discoverability.

Users could technically place an item on the half hour, but the interface did not clearly communicate which half-hour target would be used during the drag.

That interaction was improved directly on `dev`.

## New drag target behavior

While dragging a timed task over a Calendar hour:

- the upper half represents `:00`
- the lower half represents `:30`
- the active half highlights visually
- the exact destination time is shown, such as `2:30 PM`
- the preview follows the pointer
- the preview clears on drag leave
- the preview clears on drop
- the preview clears on drag end

# 10. Important Product Decisions Made Today

These decisions are useful to preserve because future work should remain consistent with them.

## Markdown remains the source of truth

Projects, tasks, milestones, publishing state, and calendar information continue to live in normal Obsidian data rather than being moved into an opaque internal database.

## Projects are open-ended

A project does not need a predetermined total task count.

Progress describes current linked work rather than making an absolute claim about total project completion.

## Project membership should be available everywhere

If a user is interacting with a task in an OnProgram task-oriented view, they should generally be able to assign or reassign that task to a Project from there.

## Do not invent dashboard metrics

The interface should not display trends, percentages, or historical comparisons unless OnProgram actually has the underlying data to calculate them.

## Views should feel like one application

Dashboard, Board, Calendar, Timeline, Projects, and Bases should share one visual language.

## Interaction state should be visible

If an action supports a finer-grained behavior—such as 30-minute Calendar placement—the UI should visibly communicate that behavior rather than forcing users to discover it accidentally.
